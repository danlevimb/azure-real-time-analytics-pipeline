# Synthetic Drone Event Contract v1.2

## 1. Purpose

Event Contract v1.2 extends the synthetic drone telemetry model with an explicit communication medium while preserving the common event envelope introduced in previous contract versions.

The main objective of v1.2 is to support heterogeneous fleets in which individual drones may communicate through either:

* `RF`
* `FIBER`

A single simulation run may therefore contain drones using different communication modes.

The normative machine-readable definition of this contract is:

```text
event_contract_v1_2.schema.json
```

---

## 2. Contract Version

Every v1.2 event MUST declare:

```json
"schema_version": "1.2"
```

The schema version identifies the structure and validation rules expected for the event payload.

---

## 3. Supported Event Types

Event Contract v1.2 supports the following event families:

```text
telemetry
state_transition
maintenance_event
status_confirmation
```

All event families share the same top-level event envelope.

---

## 4. Common Event Envelope

Every event MUST contain the following fields:

| Field                    | Type      | Description                                       |
| ------------------------ | --------- | ------------------------------------------------- |
| `schema_version`         | string    | Contract version. Must be `1.2`.                  |
| `event_id`               | string    | Unique event identifier.                          |
| `event_type`             | string    | Event family.                                     |
| `event_time`             | date-time | UTC event timestamp.                              |
| `drone_id`               | string    | Drone producing the event.                        |
| `battalion_id`           | string    | Battalion associated with the drone.              |
| `mission_id`             | string    | Mission associated with the event.                |
| `source_sequence_number` | integer   | Per-source sequence number. Minimum value is `1`. |
| `source_type`            | string    | Must be `virtual_drone`.                          |
| `source_gateway_id`      | string    | Logical source gateway identifier.                |
| `simulation`             | object    | Simulation execution metadata.                    |
| `payload`                | object    | Event-specific payload.                           |

The top-level object does not permit unspecified properties.

---

## 5. Simulation Metadata

The `simulation` object MUST contain:

| Field              | Type    | Description                         |
| ------------------ | ------- | ----------------------------------- |
| `simulator_run_id` | string  | Unique simulation run identifier.   |
| `scenario`         | string  | Scenario executed by the simulator. |
| `seed`             | integer | Deterministic simulation seed.      |

Example:

```json
"simulation": {
  "simulator_run_id": "RUN-FLEET05-V12-MIXED-CLOUD-002",
  "scenario": "mixed_communication_baseline",
  "seed": 20260924
}
```

# 6. Telemetry Event

A telemetry event uses:

```json
"event_type": "telemetry"
```

Its payload MUST contain:

```text
position
movement
power
health
communications
operations
consumables
```

---

## 6.1 Position

```json
"position": {
  "latitude": 72.000000,
  "longitude": -40.000000,
  "altitude_m": 120.0
}
```

Validation rules:

* `latitude`: `-90` to `90`
* `longitude`: `-180` to `180`
* `altitude_m`: greater than or equal to `0`

---

## 6.2 Movement

```json
"movement": {
  "ground_speed_mps": 20.0,
  "vertical_speed_mps": 0.0,
  "heading_deg": 45.0
}
```

Validation rules:

* `ground_speed_mps` MUST be greater than or equal to `0`
* `vertical_speed_mps` may be positive, negative, or zero
* `heading_deg` MUST be greater than or equal to `0` and less than `360`

---

## 6.3 Power

```json
"power": {
  "battery_pct": 97.5
}
```

`battery_pct` MUST remain between `0` and `100`.

---

## 6.4 Health

```json
"health": {
  "platform_health": "NOMINAL"
}
```

`platform_health` represents the current platform health state generated by the simulator.

---

## 6.5 Communications

Event Contract v1.2 introduces an explicit communication mode:

```json
"communications": {
  "connection_state": "CONNECTED",
  "communication_mode": "RF"
}
```

`communication_mode` MUST be one of:

```text
RF
FIBER
```

This attribute is evaluated independently for each drone.

Consequently, a fleet MAY contain both RF and fiber-connected drones during the same simulation run.

---

## 6.6 Consumables

Telemetry events MUST contain:

```json
"consumables": {
  "optic_fiber_remaining_m": null
}
```

The meaning and valid type of `optic_fiber_remaining_m` depend on `communication_mode`.

### RF drone

When:

```json
"communication_mode": "RF"
```

the value MUST be:

```json
"optic_fiber_remaining_m": null
```

An RF-connected drone does not consume an optic-fiber spool.

### FIBER drone

When:

```json
"communication_mode": "FIBER"
```

the value MUST be numeric and greater than or equal to zero:

```json
"optic_fiber_remaining_m": 8421.5
```

This value represents the remaining onboard optic-fiber capacity available to the drone.

The field remains present in both communication modes so downstream consumers receive a stable telemetry structure.

---

## 6.7 Operations

```json
"operations": {
  "asset_state": "OPERATIONAL",
  "mission_status": "ACTIVE",
  "mission_phase": "TRANSIT"
}
```

The operations object contains the current platform and mission lifecycle states.

Required fields:

```text
asset_state
mission_status
mission_phase
```

---

# 7. Communication-Mode Semantics

The principal behavioral rule introduced by v1.2 is:

```text
communication_mode = RF
    -> optic_fiber_remaining_m = null

communication_mode = FIBER
    -> optic_fiber_remaining_m >= 0
```

This relationship is enforced by the JSON Schema and is part of the event contract itself.

It prevents semantically invalid combinations such as:

```json
{
  "communication_mode": "RF",
  "optic_fiber_remaining_m": 7500.0
}
```

or:

```json
{
  "communication_mode": "FIBER",
  "optic_fiber_remaining_m": null
}
```

---

# 8. Mixed Fleet Support

Communication mode belongs to the individual drone rather than the fleet as a whole.

For example, the same fleet may contain:

```text
DRN-001 -> RF
DRN-002 -> FIBER
DRN-003 -> RF
DRN-004 -> FIBER
DRN-005 -> RF
```

Each emitted telemetry event carries its own `communication_mode`, allowing downstream processing to distinguish communication technologies without relying on external configuration state.

This enables scenarios such as:

* RF jammer degradation
* RF communication loss
* fiber-link failure
* fiber exhaustion
* heterogeneous fleet operations
* communication-specific reliability analytics

# 13. Changes from v1.1

Event Contract v1.2 preserves the existing event envelope and event families while extending telemetry communication semantics.

Primary changes:

1. `payload.communications.communication_mode` is required.
2. Communication mode is explicitly restricted to `RF` or `FIBER`.
3. `payload.consumables.optic_fiber_remaining_m` remains structurally present in telemetry events.
4. RF telemetry requires `optic_fiber_remaining_m = null`.
5. FIBER telemetry requires a numeric `optic_fiber_remaining_m >= 0`.
6. Communication mode is modeled per drone, enabling heterogeneous mixed fleets.

These changes allow downstream analytics to distinguish communication technologies directly from the event stream while maintaining a stable telemetry payload shape.

---

# 14. Validation Philosophy

Event Contract v1.2 intentionally enforces structural and semantic consistency at the producer boundary.

The contract rejects:

* unsupported schema versions
* unsupported communication modes
* missing required telemetry sections
* invalid geographic ranges
* invalid battery percentages
* negative fiber capacity
* fiber capacity attached to RF telemetry
* missing fiber capacity for FIBER telemetry
* unexpected properties inside contract-controlled objects

The objective is to prevent malformed or semantically inconsistent events from silently propagating into the streaming analytics layer.
